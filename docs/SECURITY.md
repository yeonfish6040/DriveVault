# Security and platform limitations

## Threat model
Protect vault names and file bytes at rest against someone who obtains a copy without the password. Argon2id derives a key from the password and random salt; XChaCha20-Poly1305 authenticates each chunk, binding its position and chunk count. A fresh random 192-bit nonce is generated per chunk on every save; uniqueness is probabilistic. Format magic, salt, ciphertext size, chunk count and approximate plaintext size are visible. Password strength remains critical. The format has not been audited. Replacing a vault with an older valid snapshot is undetectable; metadata and access patterns are not hidden.

The key and entered password are zeroized where practical; decrypted contents, temporary clones, OS caches, swap and application buffers are not securely erased. A compromised machine, administrator or user process may read memory, credentials or content. The temporary Basic credential is displayed in the terminal, and HTTP is unencrypted over loopback. Another local process can connect if it obtains that credential. No cross-origin or DNS-rebinding defense has been established. Never expose the server through a proxy or port forward.

## Reliability
A vault holds a lifetime exclusive OS file lock. The persistent `vault.lock` file must not be deleted while any process is active. Noncooperating tools and filesystems with broken locking remain outside this guarantee. A save validates the content tree, keeps previous ciphertext in `vault.bak`, flushes a private same-directory temporary file, then atomically replaces `vault.dat` using tempfile persist. Errors before commit roll RAM back. Directory fsync after commit is best effort: power-loss durability on removable media is not established. Snapshot reads are bounded before allocation. Failed ordinary temporary saves are cleaned up; a crash may leave encrypted temporary files.

`vault.bak` is one previous generation, not a complete backup history. For manual recovery: stop every VaultDrive process, preserve copies of vault.dat and vault.bak elsewhere, copy vault.bak over vault.dat, then unlock normally to authenticate the restored snapshot. A backup can also be damaged; there is no automatic recovery selector. A valid older snapshot can be replayed undetected.

GUI exit signals shutdown and waits for its worker, including key derivation and blocking file writes. The controlled GUI server allows five seconds for client draining, then closes remaining connections; blocking writes already in progress still finish before its runtime drops. Clients may lose unsubmitted changes. An OS/filesystem operation itself can hang; no forced thread cancellation or strict process-exit deadline is promised. Upload bodies are limited to 32 MiB and 30 seconds. Disk/encryption dispatch runs on blocking workers rather than the async executor. Browser-Origin requests are rejected; native-client credentials still need protection. Connection/resource exhaustion by a local attacker is not fully mitigated.

## Platform and plaintext export
See PORTABILITY.md for platform dependencies, unsigned application distribution and writable-mount limitations. No administrator/root escalation is executed by the app. Native clients may require user approval or OS configuration. Automatic connection is a best-effort file-manager launch and never embeds a password in an argument or URL. It does not guarantee mount or unmount.

Decrypt intentionally creates plaintext in a new private directory while retaining the encrypted source. Ordinary errors clean partial exports; a crash or force kill can leave partial plaintext. Vault filenames are validated before export. There is no secure erasure of plaintext, snapshots, process memory or external application caches. Credentials and entered passwords are zeroized where practical; the decrypted tree and GUI/OS buffers are not comprehensively scrubbed.

## GUI Guest capability access

The GUI supports native-client Guest connections by requiring an unguessable per-session 192-bit token in every vault path. The bare root and wrong-session paths return 404 without an authentication challenge; root OPTIONS reveals only DAV capabilities. Directory responses and MOVE destinations remain under the same token prefix. Browser-Origin requests are rejected. The listener remains loopback-only. Locking stops the server; unlocking generates a new token. Anyone who obtains the full URL can access the unlocked session, and another local process may observe native-client arguments/history. This is a bearer credential, not isolation from a compromised local machine. The CLI retains HTTP Basic authentication.
